# 总结接力专项决策与低 Token 架构策略

> 状态：质量优先策略已落地；接力默认由源任务模型生成结构化摘要并严格校验，脚本快速胶囊已退出默认路径；无确认回合投递已获得真实运行证据
>
> 范围：接力判定、接力成本控制、本地自调优、分阶段验收
>
> 上位策略：[《小新 Token 效率战略与分阶段执行计划》](TOKEN_EFFICIENCY_STRATEGY.md)
>
> 证据边界：当前本地实现、真实接力与无确认投递样本、Codex 本地事件与协议、OpenAI 官方文档
>
> 非目标：自动替用户接力、读取或展示私有 reasoning、以单一阈值替代判断、对外上传会话内容

## 1. 专项目标与从属关系

“总结并新开”不是上下文占用达到某个百分比后必做的清理动作，而是一项有成本、有连续性风险的任务迁移。它只有在预计收益大于迁移成本时才有价值。

本策略的核心目标是：

> 在不中断有效工作的前提下，判断继续当前任务、依赖 Codex 原生压缩，还是执行安全接力，哪一种选择能带来更高的任务净价值。

接力不再定义产品本身。小新的上位目标是在任务质量不下降的前提下减少可避免的 Token 消耗；任务配置优化和执行健康监控优先于接力扩张。总结并新建只在严重连续性损伤、自然阶段切换或用户明确要求时，作为低频恢复工具。

本专项必须服从上位策略的证据纪律：原生 compaction 默认优先，压缩次数或上下文百分比不能单独触发接力；没有反事实证据时不能声称接力已经节省 Token。

## 2. 为什么不能只看上下文阈值

当前实现以观察阈值和高风险阈值为主，并把累计压缩次数作为风险信号。这种方法简单，但会产生三个系统性问题：

1. 上下文占用高不等于任务即将失败。Codex 的原生 compaction 本来就会在长任务中降低上下文压力并保留状态。
2. 接力本身会消耗 Token。源任务总结、目标任务注入和确认回复都可能形成一笔可观的额外成本。
3. 阈值与正在执行的内部动作可能互相触发。Guardian 发起总结时重新激活红色源任务，可能反过来触发“高风险恢复”提示。

因此，**健康状态**与**干预等级**必须分开：橙色或红色可以表示需要关注，但不自动等于应该弹窗或立即接力。

## 3. 已验证的成本样本

现有一个真实接力样本提供了机制层面的证据：

| 环节 | 输入 Token | 缓存输入 | 非缓存输入 | 输出 Token |
| --- | ---: | ---: | ---: | ---: |
| 源任务生成交接摘要 | 214,129 | 210,048 | 4,081 | 3,839 |
| 新任务仅确认收到 | 30,439 | 6,912 | 23,527 | 65 |
| 合计 | 244,568 | 216,960 | 27,608 | 3,904 |

这一样本中，仅“确认收到”就占“非缓存输入加输出”成本约 75%。新任务的上下文压力从约 11.78% 很快上升到 57.26%、79.24%，随后一次原生压缩又降至约 21.16%。这说明在接近 80% 时机械接力，可能与即将发生的原生压缩重复，并造成两三轮重任务一次的接力振荡。

这只是一个样本，足以证明当前机制有优化空间，但不足以推出全局最优阈值。后续策略必须以本地观测和影子评估逐步校准。

官方机制也支持这一边界：OpenAI 将 [compaction](https://developers.openai.com/api/docs/guides/compaction) 定义为在保留状态的同时降低上下文占用、平衡质量、成本和延迟的能力；[prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) 会降低重复前缀处理成本，但缓存 Token 仍参与速率限制，不能被视为零成本。评估应遵循[模型使用建议](https://developers.openai.com/api/docs/guides/latest-model)，在代表性任务上同时比较质量、总 Token、延迟和成本。

## 4. 决策模型

### 4.1 北极星指标

每次决策比较三个候选动作：

- 继续当前任务；
- 继续当前任务并依赖原生压缩；
- 在当前有效工作单元结束后接力。

接力的期望净价值定义为：

```text
接力净价值
= 预计避免的任务损失
+ 预计未来节省的 Token 与延迟
- 接力自身 Token 成本
- 连续性损失风险
- 对用户的打断成本
```

只有当净价值为正、证据置信度足够高且通过安全门禁时，才向用户推荐接力。

### 4.2 两个独立估计器

决策由两个估计器共同完成，避免把所有信息压成一个百分比。

**连续执行风险估计器**预测未来 1～3 个有效工作单元内是否可能出现：

- 上下文压力持续上升且原生压缩未能恢复；
- 重复读取、重复解释或计划漂移；
- 关键约束、文件或验证状态开始丢失；
- 压缩后短期内再次快速逼近高水位；
- 任务失败、停滞或需要用户重新说明。

**接力经济性估计器**预测每种接力方式的：

- 源侧生成成本；
- 目标侧注入成本；
- 到首次有效动作的时间；
- 摘要缺失导致返工的概率；
- 预计需要多少后续工作，才能收回接力成本。

单一上下文阈值只作为特征之一，不能单独触发高风险弹窗或接力动作。

## 5. 健康状态与干预等级

### 5.1 健康状态

健康状态描述事实，不直接规定动作：

- **稳定**：压力、压缩恢复和语义连续性正常；
- **关注**：压力升高或出现早期连续性信号，但仍可正常工作；
- **高风险**：多个独立证据共同表明继续工作可能造成明显返工或失败；
- **故障/停滞**：已发生失败、长时间无进展或需要用户处理。

压缩次数必须采用近期窗口，例如最近三个有效工作单元，而不是任务生命周期累计次数。单次原生压缩不是异常；判断重点是压缩后的恢复质量、短期反弹速度和语义连续性。

### 5.2 干预等级

干预从低到高分为：

1. **观察**：仅更新卡片状态，不通知；
2. **非模态关注**：卡片显示风险原因和最后更新时间；
3. **本轮结束后建议**：任务完成一个有效工作单元后，提示继续或接力；
4. **快速接力入口**：用户可选择低成本接力或完整接力；
5. **紧急人工处理**：仅用于真实失败、停滞或等待用户，不因上下文占用单独触发。

运行中的任务不弹高风险模态提示。默认决策点是 `task_complete` 之后；等待批准、等待回答或明确失败可作为例外。

### 5.3 防打扰约束

- Guardian 自己发起的总结、内部任务和子 Agent 活动不参与用户风险提醒；
- 弹出提示前重新读取当前风险，历史红色状态不能直接沿用；
- 同一任务、同一原因设冷却和去重；
- 风险下降后自动撤回未处理提示；
- 用户选择“继续”后，在发生实质变化前不重复提示；
- 采用迟滞区间，避免在阈值附近反复变色；
- 设置每任务和每活跃小时的提醒预算。

## 6. 质量优先的低频接力

接力已经是严重连续性损伤、自然阶段切换或用户明确要求时的低频动作。此时主要目标是恢复质量，而不是继续压低摘要本身的 Token。系统应选择“具有源任务完整语义、且通过完整性校验的最高质量方案”。

### Tier 0：继续或依赖原生压缩

语义连续性健康时不接力。上下文占用高但压缩恢复正常，仍属于继续当前任务的合理状态。

### Tier 1：源任务模型结构化摘要

Guardian 请求拥有完整当前上下文的源任务模型生成结构化摘要，必须覆盖：

- 目标；
- 已验证完成项；
- 当前状态；
- 未完成工作；
- 不可变约束；
- 工作区、分支和关键文件；
- 已执行的测试、构建和结果；
- 必要的本地引用、路径或摘要哈希。

生成提示要求模型以最近仍有效且得到用户授权的目标为准，把旧交接摘要、控制指令、路由授权和短确认视为历史证据，不自动提升为目标或下一步。未知内容必须标记待验证，不得猜测；质量和连续性优先于摘要长度。

Guardian 随后确定性校验七个一级章节均存在且非空，拒绝嵌套的旧 `<tokenpet_handoff>` 包装。校验失败时不创建目标任务，源任务保持可追溯。

### Tier 2：结构化检查点辅助修复

执行健康阶段持续维护的结构化事实检查点用于发现摘要缺项、陈旧状态或连续性冲突，也可以作为模型修复摘要的证据输入。检查点本身不承担语义总结，确定性脚本不得从最近消息猜测目标和下一步。

### 已退出默认路径：启发式快速胶囊

真实任务已经出现把控制指令、一次模型授权或短确认错误提升为目标的样本。现有编译器只保留为历史账本兼容、隐私过滤回归和诊断工具，不再参与用户接力的默认决策。

## 7. 目标任务注入策略

当前“创建新任务 → 注入完整交接 → 要求模型回复一句确认”的流程会让确认本身成为一次昂贵模型调用。目标架构要求：

- 创建空任务时不触发确认回复；
- 交接胶囊以一次性上下文供第一次真实用户请求使用；
- 第一次模型输出直接产生有效工作，不生成纯确认消息；
- 注入完成后清除一次性状态，避免后续轮次重复携带；
- 若注入失败，保持源任务不变并明确告知用户。

本机 Codex app-server 的当前实验协议明确提供 `thread/inject_items`：它把原始 Responses API item 追加到线程的模型可见历史，但不启动用户回合。Guardian 因此把胶囊包装成普通 `role=user` / `input_text` 历史项；不使用高优先级且可能粘住后续回合的 `developerInstructions`，也不产生模型确认输出。

这里的“一次性”指只追加一次普通历史事实，而不是建立每回合重复注入的临时状态，因此没有额外状态需要清除；后续行为与任务自身已有用户历史相同，并由 Codex 原生历史和压缩机制管理。若当前 app-server 不支持该方法或注入失败，Guardian 回退到原确认回合以保持兼容性，并在成本账本中区分两种投递方式。

## 8. 自我进化与调优

### 8.1 先影子评估，不直接在线学习

单个用户的真实接力次数稀少，直接训练复杂模型容易过拟合。第一阶段让新策略在影子模式中记录“如果启用会如何建议”，但不向用户展示，也不改变行为。

仅记录隐私安全的派生数据：

- 特征向量和策略版本；
- 候选建议、置信度和原因码；
- 用户最终选择：继续、稍后、快速接力或完整接力；
- 接力方法、Token 分类、延迟、胶囊大小和校验结果；
- 后续 1、3、5 个有效工作单元内的压缩、纠正、失败和完成结果。

默认不记录完整消息、私有 reasoning 或原始工具输出。

### 8.2 不能优化“接力接受率”

用户点击接力不等于策略正确；频繁恐吓也可能提高点击率。真正需要优化的是：

- 接力前后净 Token 差；
- 交接完整性；
- 用户重新解释或模型纠正率；
- 新任务到首次有效动作的时间；
- 错误提醒率；
- 每活跃小时打断次数；
- 最终任务完成质量。

### 8.3 反事实与版本漂移

用户接受或拒绝建议会造成选择偏差：无法同时观察“接力”和“继续”的真实结果。初期采用影子评分、历史离线回放和保守更新，不把单次选择当作标签。

模型版本、上下文窗口和 Codex Desktop 协议变化后，旧数据可能失效。策略按模型、上下文窗口和任务强度分段校准；每次模型或协议大版本变化应衰减旧权重或重新进入影子期。

在有足够数据前，优先使用可解释的本地校准、受约束规则和简单统计模型。只有稳定证明净收益后，才考虑 contextual bandit 等复杂方法。

## 9. 分阶段实施契约

### Phase 0：纠正现有判定

- 抑制 Guardian 自触发的总结和内部任务提醒；
- 展示提示前重新核对当前风险；
- 活跃执行期间不弹模态提示；
- 引入迟滞、原因去重、提醒预算和自动撤回；
- 将累计压缩改为近期压缩恢复与语义信号。

验收：Guardian 自己的总结不会触发高风险提醒；当前绿色或橙色任务不会因历史红色状态弹窗；用户选择继续后不会无变化重复提醒。

当前实现状态：已完成。自动恢复警告现在要求当前风险仍为红色、存在近期压缩或压缩反弹证据、rollout 明确处于等待用户状态，并排除 Guardian 正在接力或用户已忽略的会话。累计压缩仍用于事实展示，但不会单独把会话永久判红；忽略状态在会话恢复绿色后自动解除。

### Phase 1：成本观测与影子策略

- 在有效工作单元结束时生成决策记录；
- 精确区分缓存输入、非缓存输入、输出和胶囊大小；
- 追踪后续 1、3、5 个工作单元结果；
- 新策略只影子运行，不提醒用户。

验收：能够回答一次建议为什么产生、接力实际花费多少、之后是否避免了失败；不采集私有内容。

当前实现状态：影子观测 v1 已完成。应用只在运行期间观察到“运行 → 完成”的真实边界时写入决策，不回填历史会话；策略版本、风险特征、原因码、置信度和 provider Token 分类均为结构化派生数据。每条决策在同一会话后续第 1、3、5 个完成回合冻结上下文压力、压缩和累计 Token 结果。真实接力使用源总结 turn ID 与目标确认 turn ID 精确回填两侧成本，并只保留摘要字符数和 UTF-8 字节数，不保留摘要正文。表容量分别限制为最近 2,000 条决策和 200 次接力。

本地聚合报告可通过 `.build/debug/codex-session-guardian-cli --shadow-report` 查看；报告不输出任务 ID 或会话内容。纠正/返工不能在不读取语义正文的情况下可靠推断，因此 v1 明确保持未知，不使用用户追加消息数量伪装成纠正率。失败事件将在确认稳定的公开事件类型后作为独立派生信号加入。

### Phase 2：事实检查点原型（退出接力默认路径）

- 实现确定性本地胶囊编译器；
- 实现字段完整性和大小校验；
- 建立严格内容白名单与硬大小预算；
- 校验失败时安全回退。

原验收目标“无需模型生成可恢复摘要”已被真实语义失败否决。保留的验收范围仅是：不包含 reasoning 和原始工具输出、事实来源可审计、不得伪造目标和下一步。

当前实现状态：传输、安全过滤、大小预算和回退代码已完成，但语义验收未通过，且已退出默认接力路径。最多从源 rollout 尾部读取 4 MiB 的编译器仅作为诊断工具保留；reasoning、工具调用与输出、补丁正文、代码块和链接不会进入结果，常见凭据赋值会被脱敏。字节上限只是确定性传输上限，不伪装成精确 Token 计数。

真实可丢弃任务暴露了两类失败：旧交接控制指令被提升为目标，以及一次模型授权被同时当作目标和下一步。这证明现有启发式胶囊只能作为事实清单原型，不能承担语义总结。当前默认路径已改为源任务模型摘要，并在创建新任务前严格校验全部章节。

### Phase 3：无确认回合的目标任务

- 创建空任务并注入一次性接力上下文；
- 移除仅回复“收到”的模型回合；
- 第一次真实请求直接进入有效工作；
- 验证一次性上下文的注入、消费和清除。

验收：目标任务不产生确认专用 Token；首次响应执行用户真实请求；协议失败不会破坏源任务。

当前实现状态：协议、代码和真实无确认投递均已验证。目标线程创建后优先调用 `thread/inject_items`，载荷只有一个普通用户消息；成功路径不调用 `turn/start`，结果中没有目标确认 turn ID，目标任务没有 `task_started`、`token_count` 或 assistant 输出。旧 app-server 或协议错误会自动使用原确认回合作为兼容回退，且账本记录 `historyInjection` 或 `acknowledgementTurn`，聚合报告可分别统计。

自动测试覆盖 Responses item 的 `message` / `user` / `input_text` 结构、无 developer/system 字段、无 turn input、零模型接力立即完成、完整源摘要仅等待源侧 provider 用量、旧账本默认解释为确认回合，以及原兼容路径成本。由于真实测试先暴露了胶囊语义错误，没有向目标任务发送首次真实请求；因此“目标第一次有效动作能正确继承检查点”仍未验证，不能把零确认传输等同于完整接力成功。

### Phase 4：受约束的本地自调优

- 用影子数据做离线回放；
- 按模型、任务强度和压缩行为校准；
- 策略版本化，支持快速回滚；
- 只有达到错误提醒率和净收益门槛后才逐步放量。

验收：新版本能用同一回放集与旧版本比较，且不会仅通过提高提醒频率获得表面收益。

### Phase 5：语义与完整总结兜底

- 加入有界语义摘要；
- 保留完整源总结作为稀有兜底；
- 明确展示不同接力方式的成本与适用原因。

## 10. 全局安全与隐私门禁

- 所有事实采集、评分和胶囊生成默认仅在本机完成；
- 创建新任务、打断源任务或执行接力必须由用户明确确认；
- 不自动归档或删除源任务；
- 不因单一阈值自动接力；
- 未识别事件或协议漂移时安全降级为只读观察；
- 用户可以查看“为什么提醒”、忽略本次、关闭此原因或关闭此任务提醒；
- 任何性能结论必须分别报告静态证据、运行证据和用户体验验收，不能互相替代。

## 11. 冻结决策

以下原则在后续实现中不应被无声改变：

1. 原生压缩优先于不必要接力；
2. 风险状态与干预等级分离；
3. 运行中的正常任务不弹高风险模态提示；
4. Guardian 自有动作不能触发用户风险提醒；
5. 接力低频发生，默认选择通过完整性校验的源任务模型摘要，质量优先于摘要成本；
6. 移除目标任务的确认专用模型回合；
7. 确定性事实检查点不得启发式伪造目标、决策和下一步；
8. 自调优先影子运行、可解释、版本化和可回滚；
9. 不用私有内容训练或校准策略；
10. 接力始终由用户确认，源任务始终可追溯。

## 12. 仍需运行验证与长期校准的问题

这些问题影响具体实现，但不改变上述产品策略：

- 建立来源明确的结构化任务契约，替代从最近消息猜测目标和下一步；
- 在语义检查点通过完整性验证后，再验证 `thread/inject_items` 目标的首次真实请求；
- Codex Desktop 协议升级后 `thread/inject_items` 的兼容性与自动回退表现；
- 是否存在不会占用源任务上下文的临时总结执行路径；
- 本地 Token 分类与用户实际 Codex 配额消耗之间的映射；
- 不同任务类型下事实检查点的最低完整性门槛；
- 模型或 Desktop 协议升级后的策略重新校准条件。

Phase 3 的无确认传输已经取得真实运行证据，但完整接力体验因语义胶囊失败仍未闭环。后续接力工作应服从上位 Token 效率路线：先完成任务配置优化，再由执行健康阶段建立可靠检查点；样本不足时只积累影子数据，不启用会改变提醒行为的在线调优。
