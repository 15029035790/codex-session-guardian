# 小新 Token 效率战略与分阶段执行计划

> 状态：产品主线已冻结，等待按阶段实施与真实样本验证
>
> 上位目标：在任务质量不下降的前提下，减少 Codex 中可避免的 Token 消耗
>
> 产品定义：**越来越懂用户工作方式的 Codex 自适应执行优化器**
>
> 隐私边界：默认本地、只读分析；不读取或展示私有 reasoning；不上传原始会话、源码、完整命令参数和工具输出

## 1. 为什么重新定义产品

多任务状态、等待提醒、审批、回复和快速跳转已经是 Island 类工具的成熟能力。小新可以保留桌宠、多任务雷达和低干扰通知作为体验入口，但不能把“多任务值班员”当作核心壁垒。

用户最初且长期存在的真实问题是：

1. 任务开始前，不知道什么模型和推理深度足以完成任务，容易为简单任务投入过高成本；
2. 任务执行后，Token 花在什么地方、是否有效，对用户近似黑盒；
3. 长会话压缩后，不知道目标、约束、决策和验证状态是否发生损伤；
4. 从外部复制的 `AGENTS.md`、skills、agents 和协作工作流，可能在每个任务中重复放大调用、子 Agent 和 review 成本；
5. 用户不希望持续盯盘，而是希望管家安静观察，只在存在明确、可执行的优化机会时提醒。

因此，会话管理、实时活动、健康状态和总结接力都只是手段。贯穿全部能力的主线是：

> **为每个任务选择最低充分智能，持续判断 Token 是否换来了有效产出，并纠正模型配置、执行过程和协作环境中的系统性浪费。**

## 2. 北极星指标与证据纪律

### 2.1 北极星指标

小新不追求绝对 Token 最少，而追求：

```text
任务 Token 效率 = 经过验证的有效任务结果 / 总 Token 消耗
```

“有效任务结果”不能用回复长度代替，至少结合适用于该任务的完成证据：

- 用户目标和验收标准是否满足；
- 测试、构建、静态检查或运行验证是否通过；
- 是否出现返工、重复修改、计划反转或用户重复纠正；
- 高风险任务是否保留了必要的审查和安全门禁；
- 用户是否接受最终结果。

### 2.2 配套指标

- 每类任务的 provider 总 Token、中位数和分位区间；
- 输入、缓存输入、推理、输出的结构；
- 一次完成率、验证通过率和返工率；
- 用户纠正次数和重复工作量；
- 模型或 effort 升降档次数及其结果；
- 建议采纳率，但不把采纳率当作优化目标；
- 每活跃小时提醒次数、误报率和撤回率；
- 相对个人同类任务基线的实际变化。

### 2.3 不伪造“已节省 Token”

没有反事实实验时，不能声称“节省了多少 Token”。产品必须区分：

- **已观测事实**：provider `token_count`、工具与任务事件、验证结果；
- **潜在优化机会**：基于历史同类任务估计的可避免消耗；
- **相关性**：配置变化与成本变化同时发生，但尚未证明因果；
- **已验证收益**：采用建议后，在可比任务上质量未下降且消耗稳定降低。

所有推荐都应展示样本量、置信度、原因和升级/回退条件。

## 3. 个人任务经济模型

Codex 用户的领域非常分散，但单个用户长期重复的任务场景有限。小新的长期资产不是通用模型排行榜，而是每个用户自己的：

```text
任务特征
+ 复杂度与风险
+ 用户质量偏好
+ 历史同类任务
+ 模型自评
+ 实际 Token 和完成证据
→ 最低充分配置与升级条件
```

### 3.1 首次安装：Token 体检

首次安装提供可跳过、可限定范围的本地只读盘点：

- 最近 30 天；
- 最近 90 天，默认推荐；
- 全部历史；
- 用户明确选择的项目。

盘点优先用确定性程序读取本地结构化事实，不把完整历史交给模型。分析内容包括：

- 任务、项目、时间、回合和完成状态；
- 历史实际记录的模型和 reasoning effort；
- provider Token 分类、压缩和缓存行为；
- 文件读取、搜索、命令、工具、修改和验证事件；
- 重试、重复读取、方案反转、子 Agent 和 review 扇出；
- 可以由公开证据确定的完成、失败和返工信号。

默认不持久化原始提示词、回复、源码、完整命令参数或工具输出。只有确定性特征无法分类、且用户允许时，才将有界、脱敏的摘要交给低成本模型；体检自身必须有明确 Token 上限。

### 3.2 我的任务地图

小新从用户历史中发现任务场景，不强迫所有用户使用统一分类。每个场景至少包含：

- 用户可修改的场景名称；
- 任务样本数和时间范围；
- 典型 Token 区间与成本结构；
- 常用模型和推理深度；
- 完成、验证、返工和纠正情况；
- 可疑浪费模式；
- 推荐起步配置；
- 有证据的升级条件；
- 推荐置信度和数据缺口。

任务场景与复杂度/风险必须分开。同一类“写文档”或“修改代码”不能固定绑定一个模型。

### 3.3 版本与时间漂移

旧模型任务可以帮助理解任务类型，不能直接证明旧模型仍是当前最优选择。所有基线按模型版本、Codex 版本、上下文窗口和时间分段；版本发生实质变化时衰减旧样本权重，并重新进入观察期。

## 4. 三项核心能力

### 4.1 任务配置优化

目标：在任务开始前推荐满足质量要求的最低成本模型与推理深度，并在能力不足时有证据地升级。

推荐结果必须包含：

- 任务场景与复杂度判断；
- 推荐模型和 reasoning effort；
- 预计适用原因；
- 历史相似任务证据；
- 置信度；
- 明确的升级条件；
- 用户覆盖入口。

默认策略是成本递增阶梯，而不是一次押中：

1. 从高置信度的最低充分配置开始；
2. 观察范围扩大、连续验证失败、语义不确定性和高风险决策；
3. 只有能力不足的证据成立时升级；
4. 不因单次工具错误、环境失败或审批等待升级模型；
5. 记录升级前后的质量、Token 和返工，更新个人基线。

### 4.2 执行健康监控

目标：解释执行过程中的 Token 消耗，检测压缩或长会话是否损伤任务连续性，并用最低代价纠偏。

小新持续维护本地结构化任务检查点：

- 当前目标和验收标准；
- 用户确认的硬约束；
- 关键决策及其证据；
- 当前计划和完成状态；
- 修改文件和验证结果；
- 阻塞、权限边界和下一步。

健康判断关注语义和行为证据，而不是压缩次数或上下文百分比本身：

- 重复读取已经充分分析的文件；
- 忘记确认过的约束；
- 无证据推翻已冻结方案；
- 重复已完成修改或验证；
- 修改范围突然越界；
- 用户反复纠正同一问题；
- 压缩后 Token 快速反弹但没有相应新产出。

处置顺序固定为：继续观察、补充单条事实、恢复结构化检查点、请求用户澄清、最后才建议总结接力。原生 compaction 是默认机制；总结并新建是低频恢复手段，因此一旦执行就以连续性质量优先，由源任务模型生成结构化摘要并通过确定性完整性校验，不再使用启发式脚本摘要节省这笔低频成本。

### 4.3 协作环境优化

目标：发现 `AGENTS.md`、skills、agents、工具和工作流中会跨任务放大 Token、却没有带来相应质量收益的配置。

能力由两部分组成：

**静态检查**识别：

- 全局强制多 Agent、最高 effort 或多轮 review；
- 触发范围过宽或内容过长的 skill；
- 重复、冲突和层层叠加的指令；
- 职责重叠的 agents；
- 无停止条件的 review/修复循环；
- 每回合重复注入的长提示和工具描述。

**运行归因**验证：

- 配置实际触发次数和任务范围；
- 子 Agent、review 和附加调用占比；
- review 发现的有效问题和重复结论；
- 配置变化前后可比任务的质量与成本；
- 额外 Token 是否换来更高通过率、更少返工或更可靠证据。

小新不得自动永久修改全局配置。推荐流程是：证据说明、最小 diff、临时试用、前后比较、用户确认、版本化落地和一键回滚。

## 5. 告警与交互原则

告警必须同时满足：

1. **影响显著**：相对个人同类任务基线存在实质异常或未来成本风险；
2. **原因可解释**：能够指出模型过配、重复工作、执行漂移或配置放大器；
3. **动作可执行**：用户现在采取某个动作有较高概率改善后续消耗或质量。

不满足三项时只记录，不打扰。上下文百分比、压缩次数、单次失败或累计 Token 不能独立触发高风险模态提示。

小新桌宠、悬浮卡片、多任务雷达和实时活动用于降低理解成本；人格化表达必须反映真实状态，不能用随机卖萌掩盖证据不足。

## 6. 分阶段执行计划

顺序是硬约束：先跑通任务配置优化；满意后进入执行健康监控并完成观察期；前两项通过后才实施协作环境优化。不得为了展示完整蓝图而同时铺开三条实现线。

### Phase 0：事实底座与策略迁移

目标：复用现有 provider Token、会话、实时活动和影子账本，建立新主线所需的数据契约；停止把接力当作北极星。

工作项：

- 定义任务、回合、模型配置、Token 分类、验证结果和推荐结果的数据模型；
- 盘点本机历史中模型、effort、Token、压缩、工具和验证字段的实际可用率；
- 将现有接力影子记录迁移为通用执行经济账本，保留兼容读取；
- 明确哪些完成与质量信号可以确定性获取，哪些保持未知；
- 更新产品文案和风险提示，不再按累计压缩次数推荐接力。

退出门槛：

- 能用 provider 事实重建逐任务、逐回合 Token 账本；
- 未识别或缺失字段不会被补成零或伪成功；
- 不保存私有 reasoning 和原始工具正文；
- 现有多任务、桌宠、实时活动、额度和接力能力无回归。

### Phase 1：任务配置优化闭环

#### 1A. 首次 Token 体检

- 本地只读扫描与数据范围选择；
- 历史任务特征提取、任务场景发现和用户确认；
- 生成“我的任务地图”和数据充分度；
- 标记潜在优化机会，不宣称反事实节省。

#### 1B. 推荐引擎影子模式

- 对新任务预测最低充分配置，但不改变模型；
- 记录用户实际选择、执行消耗、验证和返工；
- 对比推荐与实际结果，校准任务分类和置信度；
- 建立模型版本变化后的重新观察机制。

#### 1C. 用户可见建议

- 只展示高置信度、可解释的起步配置；
- 显示一条推荐和升级条件，不制造选择负担；
- 用户可以采纳、覆盖、对该场景固定偏好或关闭建议；
- 第一阶段不自动修改任务模型和 effort。

#### 1D. 受控自适应

- 在用户允许的任务类别中试运行成本递增阶梯；
- 比较采纳前后同类任务的 Token、完成质量和返工；
- 版本化推荐策略并支持回滚；
- 样本不足时保持保守默认，不强行个性化。

Phase 1 退出门槛：

- 用户确认任务地图基本符合真实工作方式；
- 推荐能解释“为什么是这个配置”和“何时升级”；
- 在一组代表性任务中，推荐配置没有降低既定质量门槛；
- 至少观察到可重复的 Token 改善，而非单个偶然样本；
- 错误降档、无效提醒和用户纠正处于可接受范围；
- 用户明确认可任务配置优化的日常价值。

当前实现进度（Phase 0 / Phase 1A 与 1B 影子底座）：

- rollout 解析器已逐回合记录 `turn_context.model` 与 `turn_context.effort`，并兼容 `thread_settings_applied`；
- 解析版本升级后会一次性重建旧游标，避免已有数据库因为停留在文件尾部而永远缺少配置字段；
- `--token-audit --token-audit-days N` 除配置覆盖率、配置切换和 provider Token 外，新增只含计数的行为画像：读取、命令、工具、修改、子 Agent、公开回复、显式验证成功和失败信号；不持久化命令正文或工具输出；
- 先按行为证据形成 `implementation`、`orchestration`、`investigation`、`commandOperation`、`toolAssisted`、`responseOnly` 等粗粒度任务形态。它们不是用户领域标签，也不直接代表复杂度；
- 推荐影子策略不把模型家族和 effort 排成统一降档阶梯。`sol/medium`、`luna/max`、`terra/high` 仅记录为用户当前使用习惯，分别源于架构/控制、冻结执行、判断密集执行的既有分工；习惯既不是质量证据，也不是推荐结论；
- 官方工作负载角色单独建模：Sol 用于 frontier capability，Terra 用于智能与成本平衡，Luna 用于成本敏感的高吞吐任务。模型角色和 reasoning effort 独立选择；`medium` 是平衡起点，`high/xhigh` 必须证明质量增益，`max` 只用于最困难的质量优先任务并与 `xhigh` 对照；
- 行为任务形态无法单独证明任务属于哪种官方工作负载。在获得 workload class、验证、纠正、范围和风险证据前，影子决策只输出“当前习惯待评测”或“实际配置不在习惯基线”，不生成替代模型；
- 2026-08-12 的真实 90 天临时数据库复验证明，具有 provider Token 的已完成回合可以形成行为画像并关联实际配置；该结果只证明数据管线可用，个人场景命名和真实质量仍待用户确认；
- 对当前习惯复验后：`sol/medium` 覆盖 58 个回合（8 个捕获到显式验证成功），可保留为平衡基线但不能证明它适合所有任务；`terra/high` 覆盖 13 个回合（3 个验证成功），下一对照项是 `terra/medium`；`luna/max` 在当前可见历史中暂无样本，未来应先与 `luna/xhigh` 对照；另有 16 个回合使用了习惯基线外配置。系统不会生成无工作负载依据的 `sol/low` 候选；
- 影子门槛遵循 OpenAI 的模型选择建议：在代表性任务上同时比较任务成功、答案完整性、证据、总 Token、延迟和成本；只有质量仍通过时，更少 Token 才算改进。参考 [Choose the right model](https://developers.openai.com/api/docs/guides/latest-model)。

首次受控对照（2026-08-12）：

- 从历史数据库中的 `terra/high` 已验证任务里抽取“上下文紧张告警策略”这一窄任务形态，冻结为同起点 Swift 实现题；两条实验臂分别使用 `terra/high` 和 `terra/medium`，只允许修改一个源文件；
- 两条实现经主控制器独立运行同一验证器，均为 `26/26`；Package 和验证器哈希保持一致。medium 额外选择了 60% 的低噪声关注门槛，high 将任意正压力计为关注，说明当前契约仍需冻结低压力语义，不能仅用可见测试通过判定质量完全等价；
- 在两条任务进入最后一次验证命令之前，provider 累计总 Token 分别为：high `121,777`、medium `148,663`。high 少 `18.1%`，但其 reasoning output 为 `443`，高于 medium 的 `313`；差异主要来自 medium 多一次工具回合及重复缓存上下文，而不是较高 effort 使用了更少推理 Token；
- 两条实现从用户消息到写入补丁约为 30 秒与 28 秒，差异不足以形成结论。最后的 SwiftPM 验证在 app-server 子沙箱中停滞，主控制器终止任务后独立验证通过；停滞产生的追加 Token 和等待时间不计入上述对照；
- 该样本证明“降低 effort 必然节省 Token”不成立，也证明单样本不能直接改写默认值。它可以触发下一次真实任务使用候选配置，后续由任务质量、Token 和延迟自动更新个人置信度。

本地 `codex-quota-router` 的接入边界：

- 该 skill 是用户当前声明的协作策略，不是 Token 最优性的证明。Guardian 将它保存为可解释策略契约，并继续通过真实样本验证；
- 路由输入必须显式包含：关键歧义、契约是否冻结、是否可机械验收、是否判断密集且跨模块、Luna 返工风险是否已有具体证据、委派是否有清晰价值，以及权限/外部写入/GUI 权限边界；
- Sol/medium 保留目标理解、事实调查、澄清、架构、权限、集成与验收。冻结且规则清晰、可机械验收的局部工作才进入 Luna/max；只有同时满足冻结、跨模块、判断密集，并有具体证据表明 Luna 返工风险显著更高时才进入 Terra/high；
- 复杂、耗时或历史上曾使用 Terra 都不是 Terra 路由依据。任何关键歧义、未冻结契约、无明确委派收益或不可委派权限都会回到 Sol/medium；
- CLI 的 `--route-task-contract <json>` 可对冻结契约运行确定性影子决策。输出始终标记 `declared-policy-not-token-validated`，直到代表性对照达到质量与样本门槛。

首次 skill 对齐对照（2026-08-12）：

- 同一告警策略任务在补齐 60% 压力阈值后，符合“冻结、单文件、可机械验收”，因此按 skill 归入 Luna 执行通道，并比较 `luna/max` 与官方 effort 对照项 `luna/xhigh`；没有让 Luna 与 Terra 竞跑；
- 两条实现均通过 `28/28`，未修改 Package 或验证器。max 用时 `119.1s`、5 次工具调用、provider Token `231,835`；xhigh 用时 `62.1s`、3 次工具调用、provider Token `113,034`；
- max 多 `105.1%` Token、慢 `91.8%`，reasoning output 为 `4,207`，xhigh 为 `1,531`。max 实现额外处理 NaN，但该行为不在冻结契约和验证器中，不能据此抵消显著成本差；
- 结论仍是单样本：不立刻把 Luna 默认从 max 改成 xhigh，但 `luna/max` 必须从“默认正确”降为“待证明质量增益”。xhigh 已进入候选试用；若后续至少 3 个可比任务、覆盖至少 2 种契约仍保持质量且改善 Token/延迟，则自动升级为本机个性化推荐；一旦出现明确质量失败则立即撤回候选；
- 两条脱敏样本已写入本地 `routing_evaluations` 账本。只保存契约/实现指纹、模型、effort、验证计数、耗时、工具次数和 provider Token，不保存提示词、源码、命令、输出或任务 ID。

### 外部证据基线与本地自适应边界

初始推荐不从零开始自研，也不等待本地大样本：

- OpenAI 对 GPT-5.6 的当前建议是：Sol 用于旗舰能力，Terra 平衡智能和成本，Luna 用于成本敏感的高吞吐；`medium` 是平衡起点，`high/xhigh` 只在测得质量增益时使用，`max` 保留给最难的质量优先任务并与 `xhigh` 对照。迁移已有配置时，保留当前 effort 为基线并测试低一档。参考 [Model guidance](https://developers.openai.com/api/docs/guides/latest-model)；
- OpenAI/Paradigm 的 EVMbench 覆盖 40 次审计中的 117 个真实高危漏洞。GPT-5.3-Codex 从 low 到 xhigh 的总体得分随 effort 上升，但 high 到 xhigh 的边际增益已经收窄，且置信区间重叠。这支持“高难安全任务保留高 effort”，不支持所有编码任务默认最高 effort。参考 [EVMbench](https://openai.com/index/introducing-evmbench/) 和[论文](https://cdn.openai.com/evmbench/evmbench.pdf)；
- 一项公开的 26 个真实 PR、四档 effort 对照显示 high 是该仓库的实用甜点，xhigh 的语义/评审质量更高，但平均成本约为 high 的 2.18 倍；该实验是单仓库、单 seed，作者明确不声称统计显著，因此只作为方向性外部证据，不写成全局规则。参考[实验原文](https://www.reddit.com/r/codex/comments/1t7dqnc/gpt55_low_vs_medium_vs_high_vs_xhigh_the/)；
- SWE-Bench Mobile 的 22 个 agent/model 配置显示，同一模型因 Agent 脚手架不同可出现最高 6 倍表现差异，简单的 defensive prompt 又比复杂提示高 7.4%。OpenAI 也报告过精简系统提示在内部编码 Agent 评测中减少 41–66% 总 Token、同时提高约 10–15% 得分。这意味着 skills、AGENTS、工具暴露和重复流程是模型/effort 评测的混杂因素，必须记录环境指纹，并把明显膨胀治理前置到 Phase 1。参考 [SWE-Bench Mobile](https://arxiv.org/abs/2602.09540) 和 [Model guidance](https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices)。

证据分工如下：

1. 官方原则和大样本公开评测提供“初始先验”，安装后立即可用；
2. 用户历史画像决定哪些任务形态最常见，并识别现有 skill/AGENTS/Agent 工作流；
3. 单个可比本地结果只把更省配置推进为“下一任务候选”，不改默认；
4. 至少 3 个可比任务、覆盖至少 2 种契约且候选无质量失败，才自动升级为本机个性化推荐；
5. 个性化推荐仍持续观测，出现明确纠正、返工或验证失败就降级并回退；模型版本、Codex 版本或协作环境指纹变化后重新校准。Guardian 当前只更新下一任务推荐，不中途切换正在执行的任务，也不静默改写用户的全局 skill；

这个门槛是可回退的个人在线调优策略，不是统计学上的通用模型排行榜。跨用户默认仍以官方原则和大样本评测为准，不从单个用户的三次任务外推。

### Phase 2：执行健康监控与自我进化观察

只有 Phase 1 通过后开始。

#### 2A. 消耗归因

- 将 Token 增长归因到读取、搜索、命令、工具、修改、验证、回复和子 Agent；
- 识别重复读取、无效返工和输出/工具结果膨胀三类首批浪费；
- 区分模型能力不足与环境、权限、工具失败。

#### 2B. 连续性检查点

- 从公开事实持续维护结构化任务契约；
- 在 compaction 前后比较目标、约束、决策、计划和验证状态；
- 不用脚本从最近消息猜测“目标”和“下一步”；检查点只作为健康证据和模型摘要校验输入；
- 检查点不替代 Codex 原生 compaction。

#### 2C. 低干扰纠偏

- 只对显著、可解释、可行动的问题提醒；
- 优先注入缺失事实或恢复检查点；
- 严重语义损伤或自然阶段切换时才提供接力；接力默认使用源任务模型生成的质量优先摘要；
- 记录提醒、采纳、撤回和后续结果。

#### 2D. 观察期

- 先影子运行，再小范围展示；
- 至少跨越多个真实长任务和多次原生 compaction；
- 对比策略版本的误报、漏报、Token、返工和完成质量；
- 观察个人基线是否逐渐稳定，而不是频繁漂移；
- 模型或 Codex 升级时重新进入校准期。

Phase 2 退出门槛：

- 能解释主要 Token 异常来自哪里；
- compaction 健康时不打扰，出现真实语义损伤时能给出证据；
- 纠偏优先级正确，总结接力保持低频；
- 长期观察没有导致持续增长的 CPU、内存或本地数据；
- 自我进化提高个性化准确度，没有靠增加提醒频率获得表面收益；
- 用户认可提醒足够安静、及时且有用。

#### 已落地的在线质量证据 v1

- 每个终态 turn 只保存匿名 ID、模型、推理深度、归一化任务形状、复杂度桶、动作数、Provider Token、时长和质量状态；不保存标题、cwd、prompt、命令、工具参数或原始输出；
- 质量状态严格区分“明确验证通过”“明确验证失败”“完成但未验证”和“中断”，普通 `task_complete` 不等于质量通过；
- 实现过程中先失败、后通过的验证以最后一次明确结果为准，避免把常见的红绿重构过程误判为最终质量失败；
- 一个候选配置在受控对照证明效率收益后进入真实任务试用；真实任务一旦出现明确验证失败就撤回候选，至少 3 个明确成功且覆盖 2 类匿名任务形状后才升级为个人推荐；
- 状态机只影响下一任务推荐，不切换运行中的任务，也不静默改写全局配置。
- Dashboard 只从已通过受控质量门槛且测得效率收益的候选中选择一条“下一适用任务”建议，同时展示真实质量样本进度和退回原基线的条件；没有合格候选时不制造建议。

#### 已落地的执行浪费归因影子账本 v1

- 每个终态回合都写入匿名阴性或阳性样本，最多保留 2,000 条，便于后续计算命中率而不是只统计告警；
- `repeated_read` 只在同一进展代内出现完全相同的读取操作时记录；发生修改、明确验证成功或 compaction 后重新计数；
- `retry_without_change` 只在工具输出明确给出失败状态后，同一进展代内以完全相同输入再次执行时记录；无法确认退出状态时不猜测；
- `output_bloat` 使用工具输出的实测 UTF-8 字节：单次达到 64 KiB，或同一操作在无进展期间累计达到 96 KiB；字节数不冒充 provider Token；
- 持久化内容只包含哈希、计数、输出字节、provider Token 分类、动作数和质量状态，不包含 session/turn ID、标题、cwd、prompt、命令、工具参数或工具输出；
- v1 只提供 CLI 只读查询，不进入 Dashboard、不提醒、不自动接力、不改变路由。

### Phase 3：协作环境优化

只有 Phase 1 和 Phase 2 均通过后开始。

#### 3A. 配置清单与静态体检

- 展示实际生效的全局、项目级指令和技能层级；
- 检测强制多 Agent、重复 review、宽触发 skill、冲突和重复规则；
- 对每项风险说明可能影响，不直接推断真实浪费。

#### 3B. 运行时配置归因

- 将子 Agent、review、skill 和工作流触发关联到任务账本；
- 识别配置变更点，比较前后可比任务；
- 为每项配置建立触发次数、Token 影响、质量收益和置信度档案。

#### 3C. 安全优化实验

- 生成最小配置 diff；
- 优先收窄适用范围，不粗暴删除质量门禁；
- 支持按任务临时试用、观察窗口和自动回退；
- 用户确认后才永久修改，保留版本和一键回滚。

Phase 3 退出门槛：

- 能发现至少一类跨任务的系统性 Token 放大器；
- 能区分值得保留的高成本质量门禁与无收益流程；
- 配置建议有运行证据，不只依赖静态风格判断；
- 试用和回滚不会污染用户工作区或改变未授权范围；
- 在质量不下降的前提下观察到持续、跨任务的效率改善。

## 7. 首轮实现边界

为了尽快验证核心价值，首轮只实施 Phase 0 和 Phase 1A/1B 的最小闭环：

- 不自动切换模型；
- 不自动修改模型、effort 或项目配置；全局 hook 只在用户显式执行安装器后合并，并由 Codex `/hooks` 再次确认信任；
- 不自动接力；
- 不使用完整历史正文训练模型；
- 不把任务标题当作可靠的复杂度标签；
- 不承诺精确节省金额或 Token；
- 不同时开发协作环境优化。

第一轮应先回答三个问题：

1. 本地历史能否可靠恢复“任务—配置—Token—质量证据”；
2. 能否把单个用户的常见任务场景归纳到用户认可；
3. 推荐的低成本配置能否在代表性任务上保持质量。

如果这三个问题不能用真实证据回答，后续阶段不得通过增加 UI 或规则复杂度掩盖核心能力不足。

### 7.1 提交前预检最小闭环

- 使用 Codex `UserPromptSubmit` 同步 hook，在提示词进入主模型前完成判断；
- 本地确定性规则优先，普通 `terra/medium` 路线不产生额外模型 Token；
- 只有当前配置昂贵且规则无法判断时，才用独立的 `sol/medium` 临时只读任务做有界分类，输入最多 4 KiB，12 秒超时并失败放行；
- 同时处理高置信度过配与能力不足：降档阈值为 0.90，升级阈值为 0.95；低置信度一律放行，不自动修改用户选择；
- 判定账本只保存会话哈希、配置、置信度、原因码、阻断结果、分类耗时和分类器 provider Token，不保存提示词、标题、cwd、transcript 路径或模型原文；
- handler 安装必须原子备份并保留其他 hook；新增或变化的 handler 仍由用户在 Codex `/hooks` 中审核信任。
- 决策提醒以小新悬浮面板为主入口：阻断事件直接弹出固定高度确认卡，菜单栏收件箱只保留为折叠的历史查看，不承担实时决策；
- 默认入口配置为 `gpt-5.6-terra / medium`。明显短文本任务推荐 `luna/medium`，契约冻结且机械可验收的执行推荐 `luna/max`，跨模块判断密集任务推荐 `terra/high`；架构、策略、权限、外部写入或不可逆决策推荐 `sol/medium`；
- 任务结束后先判质量：验证通过才允许把 Token 和速度计入正向效率证据；验证失败或中断建议下个同类任务按 `terra/medium → terra/high → sol/medium` 升级；只完成但未验证必须标记为证据不足，不能训练或推广更低配置；
- 被阻断的原始消息通过权限 `0600` 的本机 Unix socket 交给小新，只驻留 GUI 进程内存。点击“切换并重放”后，Guardian 写入 20 秒有效、仅匹配会话哈希与消息哈希的一次性旁路，再通过 Desktop owner IPC 在同一任务的 `turn/start` 中覆盖 model/effort 并重放；不修改全局默认，也不把原始消息写入 SQLite。

## 8. 现有能力的重新归位

- **桌宠与悬浮卡片**：低干扰的人格化入口；
- **多任务雷达**：扩大观察范围，不是独立壁垒；
- **实时语义活动**：Token 归因和健康判断的事件源；
- **额度与上下文**：预算事实和辅助特征；
- **Guardian 收件箱**：高置信度建议和异常的低噪声入口；
- **总结并新建**：严重连续性损伤或自然阶段切换时的恢复工具；
- **影子账本**：从接力专项扩展为通用任务经济观测底座。

专项接力机制、成本和安全边界继续记录在[《总结接力专项决策与低 Token 架构策略》](HANDOFF_STRATEGY.md)，但其决策必须服从本文的 Token 效率北极星与阶段门禁。

## 9. 冻结原则

1. 优化有效任务结果对应的 Token，而不是追求绝对最少；
2. 先观察和推荐，再自动干预；
3. 个性化来自用户自己的可验证历史，用户可以纠正；
4. 模型自评是特征，不是最终裁判；
5. 推荐必须给出证据、置信度和升级/回退条件；
6. 原生 compaction 默认优先，压缩次数不是风险结论；
7. 没有反事实证据时不声称已经节省；
8. 全局配置优化必须可试用、可审计、可回滚；
9. 默认本地和内容最小化，不读取或展示私有 reasoning；
10. 每阶段必须通过真实任务和用户体验验收，未通过不得铺开下一阶段。
